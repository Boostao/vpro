# Deterministic Vegetation Optimization & Duplicate Diagnosis Policy

**Status: approved and implemented (`app/internal/projectops/optimizeveg.go`, 2026-11-15).** This policy intentionally replaces the unsafe legacy behavior of `V7mdlOptimizeVeg.OptimizeVeg` (canonical SaveAsText, lines 4–65) while retaining the independent read-only duplicate diagnostic (`V7mdlOptimizeVeg.Check4DuplicatedSpecies`). A clean duplicate diagnostic does **not** imply a safe merge, because the optimizer groups across layers; see historical diagnostic notes in [VEGETATION_DUPLICATES.md](../../../archive/sep2026-r-prototype-notes/VEGETATION_DUPLICATES.md) and full-run VM evidence in `r/data-raw/oracle/veg-optimize-full-oracle.json`.

## Read-only duplicate-species diagnostic oracle (`USysAllVeg`)

`vpro_vegetation_duplicates(context)` in `r/` and the read-only duplicate diagnostic in `app/` implement `V7mdlOptimizeVeg.Check4DuplicatedSpecies` (canonical SaveAsText, lines 67–137) over the 12-branch cover-column unpivot in `Queries/USysAllVeg.txt` (lines 1–20):

- **Scope & `UNION` deduplication:** Checks the complete active project (even when an active `*_SU` filter is selected). Each non-null `Cover1`–`Cover7`, `Cover5a`–`Cover5c`, `TotalA`, and `TotalB` value becomes a `(PlotNumber, Species, MyLayer, Cover)` tuple combined via `UNION` (not `UNION ALL`), so identical `(PlotNumber, Species, MyLayer, Cover)` tuples collapse before grouping. Findings identify groups with `> 1` distinct non-null cover value (`n_of_spp` integer count). Null `PlotNumber`/`Species` keys remain eligible; blank `""` species stays distinct from `NULL`.
- **Excluded columns:** `Cover8`–`Cover10` and the physical `Layer` column do **not** participate in `USysAllVeg` or the duplicate diagnostic.
- **UI `FilterOnLoad = False` DAO verification:** Although the saved `USysAllVeg` query carries a UI `Filter` for layers `1`, `2`, `3`, and `A`, its `FilterOnLoad` property is `False`. A Windows Access 16.0 DAO probe on a disposable front-end copy returned **`129` `MyLayer='4'` records** from `SELECT Count(*) FROM USysAllVeg WHERE MyLayer='4'`, confirming the SQL/DAO execution path applies no UI layer filter.
- **Order sensitivity of legacy `First()`:** Reversing insertion order in the disposable DAO aggregate probe flipped `First(Collected)`, `First(Flag)`, and `First(Cultural1)` from `FIRST` to `SECOND` while `Max(Cover1)=2` and `Max(Cover4)=4` remained unchanged, proving legacy `First()` picks are non-deterministic.
- **Reproducible VM evidence:** Captured in `r/data-raw/oracle/{modVegOptimizeProbe.bas,run-veg-optimize-probe.ps1,veg-optimize-oracle.json,veg-optimize-oracle.tsv}` against a cloned front-end copy whose before/after SHA-256 matched `01481B94569C7172F32A812E65365F78CEA5E440DD63220D91A37DADE5778423`.

## Full-run oracle: what the legacy code actually did

The Windows Access 16.0 runner `r/data-raw/oracle/run-veg-optimize-full-probe.ps1` copied the entire `VPro64` folder to a timestamped local temp directory, verified the copy hash, and imported `modVegOptimizeFullProbe.bas`. It imported a renamed copy of the original `V7mdlOptimizeVeg` module, suppressing modal message boxes and replacing diagnostic prompt text for noninteractive execution; the check, aggregation, template copy, append, delete, reinsertion, and cleanup paths were left intact. Only in that disposable front end, it copied the 44-field `USysVegTable` into `zOracle_Veg`, inserted three records, and repointed the copied `USysAllVeg` query to that scratch table so the private duplicate check would see the same fixture. The renamed `OracleOptimizeVeg("zOracle_Veg", True)` ran to completion. It did **not** optimize the 1,633-row `Sample_Veg` project table. The original front-end SHA-256 before/after and the copy's initial hash all matched `01481B94569C7172F32A812E65365F78CEA5E440DD63220D91A37DADE5778423`.

## Audit-reference oracle on a disposable front-end copy

A follow-up Access 16.0 run used the same cloned front end and the same renamed optimizer on `zOracle_Veg`, but inserted three tagged `_Veg` audit events into the **copied** `Sample_Audit` for plot `108050` (an existing `Sample_Env` plot). The IDs `101`, `202`, and `303` matched the fixture's vegetation rows before optimization. The duplicate check returned zero; the optimizer completed; all three audit events remained with their original IDs, and a `(PlotNumber, ID)` join to `zOracle_Veg` matched **none** afterward. This includes the singleton's audit event: its vegetation ID was regenerated even though its row was not merged. The original `Sample_Veg` stayed at 1,633 rows. The source front-end hash before and after, and the initial clone hash, all matched `01481B94569C7172F32A812E65365F78CEA5E440DD63220D91A37DADE5778423`. Reproducible source is `r/data-raw/oracle/modVegOptimizeFullProbe.bas` with `run-veg-optimize-full-probe.ps1`; retained output is `r/data-raw/oracle/veg-optimize-audit-oracle.tsv` (lines 150–171).

The VBA optimizer never updates an audit table; this probe additionally demonstrates that **no automatic audit repair occurred in this fixture**. It does not prove that a bound form's audit-history display or restore action behaves a particular way after optimization, nor that every production project has the same relationship configuration. The Access observed behavior is loss of row-level audit linkage, not a safe or approved package policy.

## Approved deterministic package policy (implemented)

1. **Scope and preview (`PreviewOptimizeVeg`):** Work on the complete explicitly selected active project (with optional explicit `PlotNumbers` filter), not silently scoped to an active SU. Partition by `(PlotNumber, Species)` under exact-byte `COLLATE BINARY` equality on non-empty `TEXT` keys; do not silently normalize case, whitespace, or null/blank keys. Produce a dry-run `OptimizeVegPreview` with old IDs, candidate survivor ID, `OldToSurvivorIDMap`, field-level `FieldDiffs`, blocking `Conflicts`, `AuditReferences`, row-count changes, and a SHA-256 `PreviewDigest`. Make no changes if unresolved conflicts exist. Keep one-row groups completely unchanged, including `ID` and `Layer` (intentional difference from Access).
2. **Survivor identity (minimum signed 32-bit `ID`):** For each multirow group, choose the row with the smallest *signed 32-bit integer `ID`* (`-2147483648..2147483647`) as the survivor; that row retains its original `ID`. Require every participating `ID` across `<Project>_Veg` to be non-null, in signed 32-bit integer range, and unique across the project (including singleton groups). Refuse the operation if any `ID` is invalid or duplicated rather than relying on physical row order or regenerating IDs.
3. **Measurements (independent numeric maxima):** Compute independent non-null maxima for the numeric cover and numeric height columns used in legacy aggregation (`Cover1`–`Cover10`, `Cover5a`–`Cover5c`, `TotalA`, `TotalB`, `Height1`–`Height6`, `Height5a`–`Height5c`, and `HeightA`). All-null inputs remain null. `HeightB` is text (`VARCHAR`) and is **not** numerically aggregated: preserve it only when its non-null values agree, otherwise surface a blocking conflict.
4. **Other fields (consensus metadata with conflict blocking):** For `Layer`, `Collected`, `Flag`, `LL`, `AF`, `DC`, `UT`, `VI`, `PV`, `PG`, `FFA`, `Cultural1`, `Cultural2`, `Other1`, and `Other2`, accept the common value if all non-null values agree (including a single non-null value among nulls); return null if all are null. Distinct non-null values (including conflicting `Layer` values) are **blocking conflicts**, never arbitrary `First()` picks or silent `Layer` loss.
5. **Safety, `_Audit` protection & confirmation gate (`ApplyOptimizeVeg`):** Before mutation, validate `VP08` `_table_metadata`, plot membership in `<Project>_Env`, and `_Audit` references to any retired `ID` (blocking affected groups unless an explicit custodian `CustodianAuditOverride` is supplied). Execute inside a single `BEGIN IMMEDIATE` SQLite transaction (`WithMetadataWriter`) using explicit column names, verify `ExpectedDigest == PreviewDigest` as the explicit confirmation gate, reserve both survivor and retired child `ID`s monotonically in `__VPRO_ChildIdentity` (never reusing deleted IDs), record full field-level and summary `oldToSurvivorIdMap` rows in `<Project>_Audit`, and verify post-mutation row counts and `PRAGMA foreign_key_check` before commit.

All five deterministic rules (minimum signed 32-bit `ID` survivor, independent numeric cover/height maxima, consensus metadata with conflict blocking, `_Audit` reference protection + `BEGIN IMMEDIATE` transaction, and explicit `PreviewDigest` confirmation gate) are **approved and implemented** in `app/internal/projectops/optimizeveg.go` and `app/internal/projectops/optimizeveg_plan.go`. The minimum-ID tie-break and non-null consensus rules are **deterministic VPro 2.0 policy choices** verified against the legacy Access 16.0 DAO probes above.
