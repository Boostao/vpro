# Read-only vegetation duplicate diagnosis

`vpro_vegetation_duplicates(context)` translates the diagnostic part of `V7mdlOptimizeVeg.Check4DuplicatedSpecies` (canonical SaveAsText, lines 67–137), using the cover-column unpivot in `Queries/USysAllVeg.txt` (lines 1–20). It checks the complete active project even when an SU is selected. Each non-null Cover1–Cover7, Cover5a–Cover5c, TotalA, and TotalB value becomes a plot/species/layer/cover record. The twelve branches are combined with `UNION`, not `UNION ALL`: identical plot/species/layer/cover values collapse before grouping. Counted findings have more than one *distinct non-null cover value* for the same plot, species, and derived layer. Cover8–Cover10 and the physical `Layer` field do not participate. Null plot/species keys remain eligible; blank species remains distinct from null.

The saved `USysAllVeg` query has a UI `Filter` for layers 1, 2, 3, and A and `FilterOnLoad = False`. A Windows Access 16.0 DAO probe on a disposable front-end copy returned **129 layer-4 records** through `SELECT Count(*) FROM USysAllVeg WHERE MyLayer='4'`. Thus the saved UI filter did not restrict the SQL/DAO path used by the diagnostic, and the package correctly applies no filter. SQLite text equality and numeric storage can differ from Access database collation and Single values; borderline comparisons still need separate oracle checks. Findings are ordered, with `n_of_spp` as an integer count. An empty data frame means no flagged groups, not that the vegetation rows are unique by species. The function does not run `OptimizeVeg`, write temporary tables, open Excel, repair rows, or change context state. Optimization groups by plot/species *without layer*. Its `Max()` aggregation chooses each cover/height maximum independently, while `First()` selects Collected, Flag, and several other fields from an unspecified source order. In the disposable DAO aggregate probe, reversing insertion order changed `First(Collected)`, `First(Flag)`, and `First(Cultural1)` from `FIRST` to `SECOND` with unchanged `Max(Cover1)=2` and `Max(Cover4)=4`. Adding ascending/descending indexes did not change the first-inserted outcome in this fixture, but this is **not** a guarantee of insertion-order semantics. The final `ORDER BY PlotNumber, Species` sorts groups, not records within each group. The production routine then copies an empty table, inserts the grouped result, deletes *all* original vegetation rows, and inserts rows from the temporary table with `SELECT *` (source lines 24–48); it has no transaction, stable retained ID rule, or declared tie-break for `First()`. A mutating API should not silently choose a `First()` rule. Design it separately with an explicit survivor/field-resolution policy and transactional safeguards, subject to user approval.

Reproducible VM evidence is in `data-raw/oracle/modVegOptimizeProbe.bas`, `run-veg-optimize-probe.ps1`, `veg-optimize-oracle.json`, and `veg-optimize-oracle.tsv`. The runner cloned the entire Access folder into a timestamped `%LOCALAPPDATA%\Temp` directory before importing the module and writing scratch tables; the original front-end SHA-256 before and after was `01481B94569C7172F32A812E65365F78CEA5E440DD63220D91A37DADE5778423` and matched the copy before opening. The scratch aggregate used the same `GROUP BY PlotNumber, Species`, `Max()`, `First()`, and final `ORDER BY` shapes, **not** the destructive `OptimizeVeg` procedure. This establishes the DAO filter path and order sensitivity, but not which row Access would choose in every production table or whether a full optimizer run would fail on a particular project schema. A subsequent complete optimizer run against a disposable scratch vegetation table, its schema/ID effects, and a proposed deterministic replacement policy are documented in [VEGETATION_OPTIMIZATION_POLICY.md](VEGETATION_OPTIMIZATION_POLICY.md).
