# Transactional SQLite succession conversion

**Status: approved implementation for normal conversion and conservative add-only recovery.** Sources: `V7mdlSuccession.Convert2Succession` and `SuccessionProject` in `../VPRO_ACCESS/VPro64_forAI/Modules/V7mdlSuccession.txt` (lines 13–109); disposable VM evidence in [SUCCESSION_CONVERSION_ORACLE.md](SUCCESSION_CONVERSION_ORACLE.md). The Access reattachment oracle proves that a half-converted project can activate and that the legacy retry is blocked. It does **not** establish that every downstream form or report works without `SuccessionPlot`.

## States and interfaces

`vpro_project_succession_status()` provides a separate read-only status/preflight result with `path`, `project`, schema state, Veg year distribution including null, Env flag distribution including null, record counts, and validation errors for incomplete, non-VP08, or missing-field projects. Keep the existing `vpro_project_is_successional()` as a narrowly defined legacy-compatible **Veg-column predicate**; do not interpret its `TRUE` as proof of a complete conversion. Require explicit caller-supplied SQLite path, project, and year for conversion; no registry inference, prompt, or Shiny dependency. Use an explicit authorization callback as confirmation and a caller-approved, verifiable backup destination before writes. Disallow conversion of the bundled `Sample` and of any file path that resolves to packaged resources; a copied project named `Sample` needs a separately reviewed policy.

| Veg has `SuccessionYear` | Env has `SuccessionPlot` | State | Default action |
|---|---|---|---|
| No | No | Unconverted | Eligible for conversion after preflight and backup |
| Yes | Yes | Structurally converted | Do not overwrite; report year/flag anomalies, require separate repair decision |
| Yes | No | Legacy partial | Refuse ordinary conversion; offer explicit recovery only after inspection and backup |
| No | Yes | Inconsistent | Refuse; require manual investigation, no automatic field removal or guessed year |

A year must be a scalar whole calendar year 1–9999 (within Access `dbInteger` signed 16-bit); this range is the implemented validation rule. Inspect all eight core project tables, VP08 metadata and required Env/Veg fields; reject missing core tables, non-VP08 metadata, missing required Env/Veg fields, wrong project, and inaccessible targets; the caller must coordinate other writers. Compare field names case-insensitively. An absent year column must be added as SQLite `INTEGER`; include an explicit range/validity check for future writes if SQLite compatibility allows it without rebuilding the table. Existing Veg IDs, plot links, indexes, foreign keys, metadata, and row contents must remain unchanged except the two new columns.

## Normal conversion transaction

1. Inspect the selected physical SQLite database **without attaching a new coordinator view**; obtain an external byte-consistent backup using SQLite `VACUUM INTO` on the source connection, and verify it opens and has matching pre-change counts/schema. Do not use a raw file copy while WAL writers may be active. Decide and document how existing contexts accessing that file are quiesced; do not leave an active DuckDB SQLite attachment caching the old schema during DDL.
2. Open a writable RSQLite/DBI connection to that file with foreign keys enabled; acquire `BEGIN IMMEDIATE`, rerun preflight **inside the transaction**, and fail without writes if the state or counts changed. Back up before the transaction or use a supported backup mechanism; do not claim that `BEGIN IMMEDIATE` itself excludes every external reader.
3. `ALTER TABLE <project>_Veg ADD COLUMN SuccessionYear INTEGER CHECK (SuccessionYear BETWEEN 1 AND 9999)` and update all existing Veg rows to the explicit year. `ALTER TABLE <project>_Env ADD COLUMN SuccessionPlot INTEGER DEFAULT 0 CHECK (SuccessionPlot IN (0,1))` is the implemented translation: all existing rows read false, new rows default false, and callers can explicitly write null, matching the Access field's nullable property. Do not rewrite the full project or renumber rows.
4. Before commit, verify both fields, expected year for every existing Veg row (including no nulls), false for every existing Env row, stable row counts and identifying values, `PRAGMA foreign_key_check` (existing violations are refused), and unchanged index/metadata definitions. Roll back on any validation or SQL error. Commit once; close the write connection. Do not update config or active-project selection until the database commit succeeds. The caller must attach and activate the converted project through a fresh coordinator after commit; any later activation failure is **not** a rollback of the committed conversion.
5. Return a structured receipt: canonical path and project, chosen year, schema state before/after, changed row counts, backup location/checksum, validation results, and whether reactivation succeeded. No silent retries and no mutation of any other project family.

SQLite DDL participates in an explicit transaction; test rollback both after adding the Veg column and after the Veg UPDATE. A failed transaction should leave both columns absent and every original value intact. Build the schema and data assertions against disposable copies of bundled Sample (renamed project) plus realistic irregular-schema fixtures, not the installed package files.

## Explicit recovery for legacy partial state

Ordinary conversion must **not** rerun when Veg has `SuccessionYear` and Env lacks `SuccessionPlot`. The separate `vpro_project_recover_succession()` action is available only if VP08 table validation and a read-only audit confirm the existing Veg years and IDs, all Env rows, no conflicting column aliases, and an external restorable backup. The implemented resolution is **preserve existing Veg years** and add only the missing Env flag; restoring a pre-conversion backup is an external operator action. Never overwrite mixed years, null years, or unexpected existing values merely because a new requested year differs. The implemented add-only recovery requires one non-null valid year across a nonempty Veg table; mixed, null, or empty Veg years remain diagnostic-only. Approval for broader historical states is not implied. Execute the approved add-only repair in its own `BEGIN IMMEDIATE` transaction, recheck partial state under lock, verify Veg values/identities unchanged and Env flags initialized as approved, then commit; attach in a fresh coordinator separately. If validation fails, roll back and report the partial state; do not delete `SuccessionYear` or infer a year.

Other inconsistent states (`Env` flag only, already-converted projects with mixed/missing Veg years, bad types or conflicting field definitions) are **diagnostic-only** until a separate policy is approved. Preserve the backup and a recovery receipt even when activation fails. The existing field-only detector may continue returning true for legacy parity, but higher-level conversion/activation UIs should consult the richer status and warn or block partial states; changing current activation behavior requires separate tests and approval.

## Implemented scope and remaining limits

`vpro_project_convert_succession()` and `vpro_project_recover_succession()` require explicit permission callbacks (`convert_succession` / `recover_succession`), an unused backup path, and optionally a valid context that does not already attach the target. They do not create, detach, refresh, or activate DuckDB contexts. The caller must quiesce other connections and attach/activate in a fresh context after commit. The receipt reports activation as not attempted. The implementation uses SQLite `VACUUM INTO` for a consistent snapshot (including WAL), verifies its status, row identities, schemas and integrity, rechecks under `BEGIN IMMEDIATE`, verifies row identities/indexes and foreign keys before commit, and retains the backup even after rollback. It rejects existing foreign-key violations rather than attempting to repair them. Tests include WAL, empty tables, authorization/guards, partial-state refusal, preservation of years/IDs, and injected failures following each DDL/update stage. Integration tests now check a realistic renamed VP08 Sample copy, a separate restored `VACUUM INTO` backup (rows, identities, schema, integrity and foreign keys), an open WAL reader, and a writer holding an immediate transaction. The writer case retains a consistent backup while conversion fails to acquire its lock and leaves the source unchanged. With `sqlite_scanner` explicitly installed, the realistic VP08-copy test now executes fresh-coordinator activation, checks `USysEnv` and `USysVegA`–`D` values, rejects attached-context conversion, and exercises an in-place restoration on the disposable copy. Offline checks still skip that branch. The package does not automate restoration or coordinate external processes.

## Tested manual restoration sequence

On a disposable project, the integration test closes its DuckDB coordinator after conversion, copies the verified `VACUUM INTO` backup over the inactive SQLite project file, compares its MD5 against the conversion receipt, inspects the restored `unconverted` state, then creates a **new** coordinator and checks restored `USysEnv`/`USysVeg` views and absence of `SuccessionYear` in `USysVegA`. A separate restored backup file is compared to the pre-conversion Env/Veg rows, row IDs, table/index schemas, foreign keys and integrity. This verifies the backup is usable, not a general-purpose restore command.

For a real restore, first stop all application writers/readers and close every DuckDB and SQLite attachment to the target; keep a separate copy of the post-conversion file and the immutable backup. Verify the receipt checksum and backup integrity and project identity before replacing the closed target. **Do not blindly overwrite a live WAL-mode database:** resolve or checkpoint sidecar `-wal`/`-shm` state under controlled SQLite shutdown before replacement, and ensure no stale sidecars or processes can replay changes onto the restored file. Reinspect schema, integrity, foreign keys and row counts, then reactivate only in a fresh coordinator. The integration test does not simulate external processes or a target with live sidecars, so this is an operator checklist, not an automatically safe production restore.
