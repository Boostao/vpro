# Proposed deterministic vegetation optimization policy

**Status: design proposal, not approved or implemented.** This deliberately differs from `V7mdlOptimizeVeg.OptimizeVeg` (canonical SaveAsText, lines 4–65). The existing read-only duplicate diagnostic remains independent; a clean diagnostic does **not** imply a safe merge, because the optimizer groups across layers and also changes singleton IDs. See [VEGETATION_DUPLICATES.md](VEGETATION_DUPLICATES.md) and `data-raw/oracle/veg-optimize-full-oracle.json` for observed Access behavior.

## Full-run oracle: what the legacy code actually did

The Windows Access 16.0 runner `data-raw/oracle/run-veg-optimize-full-probe.ps1` copied the entire `VPro64` folder to a timestamped local temp directory, verified the copy hash, and imported `modVegOptimizeFullProbe.bas`. It imported a renamed copy of the original `V7mdlOptimizeVeg` module, suppressing modal message boxes and replacing diagnostic prompt text for noninteractive execution; the check, aggregation, template copy, append, delete, reinsertion, and cleanup paths were left intact. Only in that disposable front end, it copied the 44-field `USysVegTable` into `zOracle_Veg`, inserted three records, and repointed the copied `USysAllVeg` query to that scratch table so the private duplicate check would see the same fixture. The renamed `OracleOptimizeVeg("zOracle_Veg", True)` ran to completion. It did **not** optimize the 1,633-row `Sample_Veg` project table. The original front-end SHA-256 before/after and the copy's initial hash all matched `01481B94569C7172F32A812E65365F78CEA5E440DD63220D91A37DADE5778423`.

Both rows of the pair passed the private duplicate check (`0` same-layer conflicting-cover findings), yet were merged across layers. Even the unmerged singleton acquired a fresh ID and lost `Layer`. The merged row retained the first source record's `Collected`, `Flag`, and `Cultural1` values in this copy, but earlier reversed-insertion aggregate probes showed that `First()` is order-sensitive. `Sample_Veg` still had 1,633 rows; temporary table and query were removed. The probe used an unrelated scratch table without the `Sample_Env` relationship or real audit references; therefore it does not establish what happens to historical audits, or whether a production project with schema drift completes successfully. The live template and original table both had 44 fields in identical order, a non-unique `ID` index, and `GenUniqueID()` default. The SQL `INSERT INTO [...] SELECT xxxtblTempVeg.*` is positional and depends on matching schema order.

## Candidate package policy (requires product approval)

1. **Scope and preview.** Work on the complete explicitly selected active project, not the active SU. Partition by `(PlotNumber, Species)` under a stated, tested equality/collation rule; do not silently normalize case, whitespace, or null/blank keys. Produce a dry-run plan with old IDs, candidate survivor ID, field-level before/proposed values, conflicts, audit references, and row-count changes. Make no changes if there are unresolved conflicts. Keep one-row groups completely unchanged, including `ID` and `Layer` (intentional difference from Access).
2. **Survivor identity.** For each multirow group, choose the row with the smallest *signed numeric ID* as the survivor; that row retains its original ID. Require every participating ID to be non-null, in signed 32-bit range, and uniquely identify one row across the project (including groups not being merged). If any are duplicated or ambiguous, refuse the operation rather than relying on physical row order or inventing replacement IDs. Provide an explicit old-ID-to-survivor-ID mapping in the plan; never silently rewrite unrelated or historical records.
3. **Measurements.** Compute independent non-null maxima for the same numeric cover and numeric height columns used in the legacy aggregation (`Cover1`–`Cover10`, `Cover5a`–`Cover5c`, `TotalA`, `TotalB`, `Height1`–`Height6`, `Height5a`–`Height5c`, and `HeightA`). All-null inputs remain null. This retains the observable Access numeric merge rule, but can combine cover and height from different source rows; disclose that in the plan. `HeightB` is text and was **not** aggregated by the legacy SQL: preserve it only when its non-null values agree, otherwise block and require explicit resolution.
4. **Other fields.** For `Layer`, `Collected`, `Flag`, `LL`, `AF`, `DC`, `UT`, `VI`, `PV`, `PG`, `FFA`, `Cultural1`, `Cultural2`, `Other1`, and `Other2`, accept a common value if all non-null values agree (including a single non-null value among nulls); return null if all are null. Distinct non-null values, including conflicting `Layer` values, are **blocking conflicts**, not arbitrary `First()` picks or silent `Layer` loss. Present conflicting values and their source IDs for explicit resolution in a separately approved workflow. Do not mix conflicting per-row metadata just to force a merge.
5. **Safety and history.** Before mutation, validate project version/schema and plot membership, detect duplicate keys/collations, confirm the duplicate-cover diagnostic and field conflicts, and check `_Audit` for references to any ID proposed for removal. Block affected groups until an approved audit-history/provenance policy exists; never silently reassign old audit events to the survivor ID. Execute any approved plan in one SQLite immediate transaction with explicit column names, preserve unchanged rows, check row counts and foreign keys, retain an external pre-change backup and an old-to-new mapping, and roll back on any mismatch. An explicit confirmation and tested restore path are prerequisites. No package optimizer should be exposed until these decisions are accepted and tested.

The minimum-ID tie-break and non-null consensus rules are **new deterministic design choices**, not claims about the legacy algorithm. The policy intentionally rejects common cross-layer cases until `Layer` and audit-history handling have explicit product decisions. No optimizer implementation is included in this milestone.
