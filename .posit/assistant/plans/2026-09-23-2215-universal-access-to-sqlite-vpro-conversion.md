# Universal Access-to-SQLite VPRO conversion

## Decisions and boundaries

- Accept an explicit `.mdb`/`.accdb` path and output destination(s). Never modify the Access source, follow linked backends implicitly, overwrite existing SQLite files, install a DuckDB extension, or invoke Access VBA conversions automatically. Detect and report links; require separately supplied paths/authorization for another file in a later operation.
- One call inventories and archives **all readable local tables in one Access file**. The archive is a faithful, inspectable SQLite extraction, **not** a VP08 project. Preserve names, every readable source field, data, nulls and row counts, plus table descriptions/available schema metadata and a source manifest. Report unsupported field types/attachment provenance rather than silently dropping them. Do not copy forms, VBA, saved queries, or relationships as executable equivalents; inventory these only when metadata permits.
- Promote an individual project family to a **separate** canonical SQLite file only after a VP08 schema/version/data preflight; preserve source-only fields and ancillary tables without renaming or dropping them. If extras cause a mismatch with package APIs or an invariant cannot be verified, return an archive and diagnostics, not a false `compatible = TRUE`. Older VP02–VP07, unknown and mixed versions remain archive-only until reviewed mappings exist. Do not carry over Access's destructive legacy conversion steps, deferred terrain narrowing, succession copying, or vegetation optimization.
- `_table_metadata` is the SQLite translation of Access TableDef `Description`. Read the source property with `mdbr::mdb_prop(path, name = table)` where available, preserving missing/unknown values distinctly in diagnostics; never fabricate VP08 metadata to pass `vpro_project_inspect()`.

## Implementation stages

1. **Inventory and extraction design.** Inspect mdbr's installed interfaces and a disposable copy of a representative Access source to establish local-vs-linked table discovery, field types, dates/blobs, identifier quoting, descriptions, and chunked reads. Audit existing `data-raw/z_initutils.R` comparison helpers before moving only broadly useful logic into `R/`; do not depend on unexported `mdbr:::` helpers in the runtime API. Record reproducible fixtures and explicitly label mdbr metadata that cannot be extracted. Provide dry-run inventory/version report first, with no output file mutation.
2. **Archival SQLite conversion.** Implement an explicit-path API (provisionally `vpro_access_archive(source_path, output_path, ...)`) that validates source/output paths, inventories all local tables, builds tables using conservative SQLite affinity mappings, streams data in bounded batches, and writes manifest and `_table_metadata` in the archive. Use a staging SQLite file, one transaction where feasible, and move to a nonexisting destination only after validation; retain no apparent-success partial output. Make failures per-table explicit rather than silently omitting an unreadable local table. Keep source-only columns, dates, numeric precision and binary values under test; document lossy encodings that cannot be prevented.
3. **VP08 promotion gate.** Implement a separate explicit project promotion API. Match eight core tables by exact suffix; inspect Env `Description` and required fields, keys, row identities, FKs, indexes, audit linkage and actual data. Translate from the checked-in canonical VP08 schema or preserve the verified source schema as appropriate; do not copy Sample data or add `NewProject` events to an existing imported family. Preserve extra columns/tables in a manner testable by the API, report deviations, and write VP08 metadata only if its semantics are proven. Keep detached/inactive after conversion. If constraints or metadata cannot be reconstructed without losing data, refuse promotion while retaining the archive. Reuse `vpro_project_inspect()`, schema comparison, integrity validation, and a fresh coordinator activation as postconditions (do not equate a simple VP08 Env tag with full safety).
4. **Historical upgrade strategy (follow-on, not automatic first release).** Inventory the exact VP05–VP07 Access INSERT mappings, earlier VP02/VP03 paths, source-only fields and omitted Admin/Metadata behavior. For each historical version require reviewed, loss-aware transformation specifications, realistic populated fixtures and preservation checks before enabling archive-to-VP08 promotion. Report unsupported versions clearly in the initial converter. Keep terrain-width, succession-copy and optimizer policies separate pending the previously deferred approvals.
5. **Validation and release.** For each table compare source/target field names, types, null counts, row counts and deterministic data fingerprints (using the existing `harmonize_validation_tables()` ideas, not `all.equal()` on whole large tables). Test text newlines, datetime semantics, blobs, booleans, duplicate IDs, orphan rows, large streamed tables, missing `Description`, corrupt/linked/unsupported tables, collisions, read failures and staged-output rollback. Use disposable Access copies only; test representative VP08 and pre-VP08 files plus synthetic SQLite/unit fixtures. Run focused and full package tests and built-package check; document scope/limitations, parity mapping only for reviewed features, and add an explicit noninteractive usage example.

## Specific evidence

- `V7mdlAttachProjects.AttachProjectTables` in `../VPRO_ACCESS/VPro64_forAI/Modules/V7mdlAttachProjects.txt:67-139` directly attaches only VP08 and routes VP05–VP07 through separate imports. `V7mdlImportVProVer05/06/07` have different table coverage; older `V7mdlVersionConversion` performs destructive replacements.
- `data-raw/projects/init.R:9-70` and `data-raw/z_initutils.R:49-164` validate fixed CSV exports through mdbr but do not accept arbitrary Access paths. `R/00.db.R:207-216` has a misleading stub that does not export data; replace/remove it only after checking callers.
- `R/project-create.R` creates *new empty* VP08 families and must not generate bootstrap audit entries for imports. `R/project-context.R` saves an existing family with history; `R/project.R` defines eight core tables; `R/project-schema.R` and `R/project-context.R` offer post-import diagnostics. `data-raw/projects/TERRAIN_SCHEMA_INVESTIGATION.md` documents why automatic narrowing is unapproved.

## Acceptance conditions

- Every local Access table has either a validated archival SQLite counterpart or an explicit blocking error; source file bytes are unchanged. An archive never masquerades as a VP08 project.
- VP08 promotion is opt-in, non-destructive, validates each core table and retained extras, and yields a package-attachable result only when independently checked. An unsupported or ambiguous historical project returns an archive plus evidence, with no fabricated VP08 compatibility.
- Failed extraction/promotion does not replace or leave a misleading target; saved receipts include source identity, table counts, versions/descriptions, conversion decisions and validation status.
